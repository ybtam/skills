# Release with Changesets

Use this skill only after the owner confirms that release automation is wanted. Inspect
the target repository first, ask the applicable decisions in
[the release workflow reference](references/release-workflow.md), record the selected
path in its approved plan, and do not infer a registry, runner, action ref, secret,
release branch, publication command, or production behavior.

Use the bundled [baseline](references/baseline.md), [questionnaire](references/questionnaire.md),
[integrations](references/integrations.md), [state](references/state.md), and
[migration](references/migrations.md) guidance when the target needs those branches.
They are distribution copies generated by this collection; do not edit them by hand.

Select exactly one release owner: copy either the native
[Changesets Action template](assets/github-actions/native-changesets-release.yml) or
the target-owned [custom owner template](assets/github-actions/custom-release-owner.yml),
alongside the pull-request [intent template](assets/github-actions/release-intent.yml).
The optional [production handoff template](assets/github-actions/production-handoff-on-release.yml)
receives only the reviewed release: published event.

For local fallback verification, copy and complete
[workflow-shape-contract.json](assets/workflow-shape-contract.json), then copy the
[workflow-shape verifier](assets/verify-workflow-shape.mjs) into the target checkout.
The contract is a reviewed target artifact, not a secret and not a generic deployment
map: it names only the workflow/job/branch/path/exemption/run facts selected by the
plan, including the native action's version/publication choice and an optional
production prerelease guard. Paths in the JSON are relative to the contract file. Its
one input replaces all prior environment-variable heuristics:

    CHANGESETS_WORKFLOW_CONTRACT=.changesets-workflow-contract.json \
      node --test path/to/verify-workflow-shape.mjs

The fallback checks only declared local workflow shape. It does not prove hidden or
unlisted release logic is safe; that remains a reviewed target-plan concern. Report
local validation, remote Actions, registry publication, GitHub Release creation, and
production actions as separate outcomes.
